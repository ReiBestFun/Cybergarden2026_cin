# CyberFlow — командная работа и локальная приёмка

Состав работ и его зависимости ведутся в [GitHub Issues](https://github.com/ReiBestFun/Cybergarden2026_cin/issues). Серверный деплой и восстановление из резервной копии исключены из текущего этапа.

## Проблема

Команда может собрать сценарий, проверить учебный Kotlin/Spring Boot-проект и получить отчёт. Текущие проекты и новые шаблоны привязаны к отдельным аккаунтам. Коллегам трудно переиспользовать настройки, а руководитель не может выдавать права по ролям и видеть, кто изменил настройки команды. GitHub уже используется для входа и запуска CI, но проверка из готовой конфигурации срабатывает после push в выбранную ветку. Публичного серверного контура с воспроизводимым запуском приложения пока нет в конфигурации проекта.

Менторы также попросили расширить каталог нод, добавить энтропию в Secrets, развить интеграции и выбор LLM, определить границы процессов, оформить правила логирования и упростить подключение MCP. Сквозная демонстрация должна подтвердить исходный кейс на учебном репозитории организаторов.

## Решение

Администратор создаёт рабочее пространство, приглашает участников с заданными ролями и управляет настройками команды. Участники совместно используют проекты, сценарии, шаблоны и историю, а персональные черновики шаблонов остаются доступными автору до публикации.

Редактор получает дополнительные ноды проверок и логики. Secrets использует энтропию вместе с форматом и контекстом кандидата. GitHub возвращает результат проверки pull request до слияния. Ollama работает по умолчанию, а администратор может явно разрешить внешний провайдер. MCP даёт ограниченный доступ к результатам и проверке черновиков.

## Решения по реализации

1. **Рабочее пространство и авторизация.** GitHub OAuth подтверждает личность. Приглашение связывает пространство, роль и срок действия, погашается один раз и проверяется сервером. Полномочия проверяются на уровне API для каждого ресурса. Перенос личных проектов, сценариев, истории и шаблонов выполняется с явным назначением владельца или пространства. Для записей без известного владельца требуется подтверждённое назначение. Сохранение доступа после удаления участника относится к ресурсам пространства, а не к его действующим полномочиям.
2. **Шаблоны.** Личный черновик видит автор. Опубликованный шаблон доступен участникам его пространства согласно правам. Копия сценария редактируется независимо. При публикации исключаются значения и ссылки на реквизиты, получатели, параметры конкретной ветки и другие привязки к проекту. Скопированное расписание изначально выключено.
3. **Ноды.** Команда расширяет встроенный каталог. Первая партия включает проверку небезопасной конфигурации Spring Boot и составное условие AND/OR. Для конфигурационных правил, которые сейчас находятся в SAST, обеспечить отсутствие дублирования при совместном запуске и сохранение покрытия существующих сценариев. Каталог описывает параметры, порты и допустимые связи. Неизвестный тип и несовместимая связь отклоняются при валидации графа.
4. **Secrets.** Энтропия применяется как один из признаков вместе с контекстом, форматом и длиной. Существующие контекстные проверки сохраняются. Значение кандидата исключается из пользовательских результатов, логов и данных для LLM. Критерии принятия находки проверяются на эталоне и дополнительных синтетических примерах.
5. **GitHub.** Различать вход через OAuth и интеграцию проверки PR. Целевой сценарий связывает результат с проверяемым SHA и возвращает GitHub явный вердикт. Критическая находка и ошибка выполнения должны препятствовать успешному прохождению обязательной проверки. Для настройки защиты ветки нужны соответствующие права на учебный репозиторий. Поддерживаемый источник для сдачи — только `TBagirov/training`; сторонние URL отклоняются до загрузки.
6. **Логирование и аудит.** Технические журналы API и воркеров используют структурированные поля: время, уровень, компонент, действие, результат, идентификатор корреляции и, когда применимо, запуск или доставку. События аудита отражают исполнителя, рабочее пространство, действие и результат. Минимальный набор включает приглашения, смену ролей, публикацию шаблонов, изменение реквизитов и настроек провайдера, выдачу и отзыв доступа MCP. Значения секретов, cookie, токены, тела запросов и исходники исключаются. Доступ к аудиту ограничен ролью.
7. **Настройки.** В интерфейсе разделены личные настройки и настройки рабочего пространства. Раздел команды охватывает участников, приглашения, интеграции, доставку и LLM. Значения уже сохранённых реквизитов не возвращаются в интерфейс. Запросы на изменение проверяют полномочия на сервере.
8. **LLM.** Ollama используется по умолчанию. Явно включаемый внешний провайдер использует тот же контракт структурированного ответа. Подключаемый профиль хранит имя модели, URL и защищённые реквизиты. Перед подтверждением администратор видит состав входных данных: для отчёта — ограниченные сведения о группах находок, для генерации — текст задания. Пути, номера строк и advisory в итоговом отчёте формируются из сохранённых результатов. При недоступности модели исходные находки и базовый отчёт остаются доступными.
9. **MCP.** Полномочия MCP выдаются отдельно, ограничены собственным рабочим пространством и доступны для отзыва. Клиент ищет или открывает доступные запуски, читает сводки и ограниченные поля находок, использует каталог и проверяет черновик. Черновики передаются для проверки в интерфейсе. Публикацию, изменение и запуск подтверждает пользователь в CyberFlow.
10. **Локальный стенд и карта процессов.** Фронтенд, API, воркер проверок с планировщиком, воркер доставки и PostgreSQL образуют локальный стенд. API и воркеры — отдельные процессы общего backend с общей БД. MCP имеет собственную точку запуска.
11. **Дополнительные сканеры.** Отдельные самописные ноды проверяют прямую передачу чувствительных значений в логгер и использование быстрых хешей для хранения или проверки паролей. Находки и отрицательные примеры проверяются на синтетических фикстурах. [#11](https://github.com/ReiBestFun/Cybergarden2026_cin/issues/11) · [#12](https://github.com/ReiBestFun/Cybergarden2026_cin/issues/12)
12. **Политика журналов.** Администратор выбирает разрешённое хранилище, сроки хранения диагностики и аудита и права на просмотр, экспорт и изменение политики. API проверяет права и изоляцию пространств. [#19](https://github.com/ReiBestFun/Cybergarden2026_cin/issues/19)

## Решения по тестированию

Приёмочные тесты проверяют внешнее поведение на самом высоком доступном уровне. Для бизнес-правил достаточно API и отдельной PostgreSQL. Браузер нужен для взаимодействия с редактором, отображения процесса и видимости настроек. Сетевые интеграции сначала проверяются на имитаторах, затем на учебном стенде.

- **API и PostgreSQL.** Продолжить существующие интеграционные тесты аккаунтов, шаблонов, запусков, расписаний и доставки. В двух пространствах с разными ролями проверить одноразовое погашение приглашения, истечение срока, отзыв, смену роли, отказ в доступе к чужим ресурсам и сохранение истории при удалении участника. Проверить миграцию копии существующей БД и видимость личного и общего шаблонов.
- **Учебный эталон и искусственные примеры.** На `TBagirov/training` сохранить 15 эталонных находок и отсутствие шести отрицательных контролей. В дополнительных фикстурах проверить токен с недостаточно информативным именем, хеш, UUID, заглушку и низкоэнтропийное значение в явно секретном контексте. Сопоставить JSON и читаемый отчёт, проверить отсутствие дубликатов между SAST и новой нодой.
- **Граф и интерфейс.** Через API проверить таблицы истинности составных условий и ошибочные параметры. В браузере собрать сценарий вручную, проверить порты, состояния нод и превью, затем отредактировать граф, созданный моделью. Убедиться, что запрещённые действия отклоняются сервером даже при прямом запросе к API.
- **GitHub, уведомления и LLM.** Проверить соответствие SHA и три исхода CI на имитаторе, затем показать статус учебного PR. Один канал доставки проверить с фактическим тестовым получателем команды. Проверить локальную модель, разрешённый внешний профиль, некорректный JSON, неверную группу находок, выдуманный CVE и сохранение базового отчёта при сбое модели.
- **Аудит и MCP.** По одному идентификатору проследить запрос, запуск и доставку. Проверить наличие событий аудита и исключение чувствительных значений. Через MCP проверить выбор запуска, изоляцию пространств, ограниченный вывод, валидацию черновика и отказ после отзыва доступа.
- **Сквозная приёмка.** На локальном стенде применить миграции, выдать приглашение, открыть пространство вторым аккаунтом, запустить сценарий и получить уведомление. Из этого запуска выгрузить оба отчёта. Проверить изменение срока хранения журналов и отказ в доступе к журналам другого пространства. [#18](https://github.com/ReiBestFun/Cybergarden2026_cin/issues/18)

## Вне объёма

- Проверки любых других репозиториев и систем в сдаваемой версии.
- Исполнение произвольного пользовательского кода внутри редактора.
- Межкомандная и публичная публикация шаблонов.
- Изменение, публикация или запуск сценариев через MCP без участия пользователя в интерфейсе.
- Разбиение backend на независимые микросервисы, несколько серверов и оркестрация кластера.
- Замена самописных анализаторов готовыми сканерами или LLM.

## Дополнительные заметки

- Исходное состояние — рабочая копия со слиянием в процессе. Критерии приёмки применяются к согласованному дереву после завершения слияния.
- Подтверждены совместное пространство, GitHub OAuth с приглашениями, один Linux-хост, расширение встроенного каталога, энтропия как дополнительный признак, PR-проверка GitHub, явное разрешение внешней LLM и ограниченный MCP.
- Для детализации остаются матрица ролей и точный состав настроек, сроки приглашений и хранения аудита, способ получения прав на учебный PR, конкретный новый внешний LLM-провайдер, следующий сервис после GitHub и способ выдачи полномочий MCP. Спецификация фиксирует требуемое поведение этих функций, сохраняя выбор деталей при реализации.
- Для демонстрации подготовить шесть частей: проблема и целевая аудитория, живое демо, ноды и алгоритмы, LLM и проверка рекомендаций, архитектура, задачи со звёздочкой и планы развития. Основание — PDF кейса, замечания менторов и [формат сдачи организаторов](https://github.com/TBagirov/training/blob/fe1fcbe212669783480666b9b60147c8a8c6eef4/docs/submission-format.md).
