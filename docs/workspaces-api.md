# Рабочие пространства — контракт API для задачи #3

API использует существующую сессию CyberFlow. Запросы отправляются с cookie, операции записи передают JSON и проходят существующую проверку источника запроса. Спецификация доступна в Swagger на `/docs`. Для запросов из Swagger войдите в приложение.

## Эндпоинты

| Метод и путь | Запрос | Результат |
|---|---|---|
| `GET /api/workspaces` | `limit`, `offset` | `200` и стандартная страница `{items,total,limit,offset}`. Первым идёт личное пространство. |
| `POST /api/workspaces` | `{"name":"Команда DevSecOps"}` | `201` и объект созданного пространства. Создатель получает роль `owner`. |
| `GET /api/projects?workspace_id=<uuid>` | `workspace_id`, `limit`, `offset` | `200` и страница проектов выбранного пространства. |
| `POST /api/projects` | Существующие поля проекта и `"workspace_id":"<uuid>"` | `201` при создании или `200`, если репозиторий уже есть в этом пространстве. |
| `POST /api/projects/{project_id}/move` | `{"workspace_id":"<uuid>" }` | `200` и обновлённый проект с тем же `id` и новым `workspace_id`. Повтор переноса в то же пространство возвращает тот же проект. |

Элемент `GET /api/workspaces` и ответ `POST /api/workspaces` имеют вид:

```json
{
  "id": "fd1c4ad3-d5f4-4c74-8df2-7806fd4d8d20",
  "name": "Команда DevSecOps",
  "personal": false,
  "role": "owner"
}
```

В этой версии `role` равна `owner` или `member`. Участник может читать проекты, сценарии и историю. Для изменения ресурсов, запуска сценариев и доступа к реквизитам нужна роль владельца. Личное пространство создаётся при первом входе, для прежних пользователей — миграцией. Без `workspace_id` список и создание проектов используют личное пространство. Все ответы с проектом содержат `workspace_id`. Дедупликация репозиториев работает внутри пространства.

Набор действующих эндпоинтов для конкретного проекта не меняется. Например, история доступна через `GET /api/projects/{project_id}/runs`, сценарии — через `GET /api/projects/{project_id}/workflows`, а результат и SSE — через `GET /api/runs/{run_id}` и `GET /api/runs/{run_id}/events`. Дополнительный параметр пространства для этих запросов не требуется. Backend определяет его по ресурсу и проверяет членство, в том числе при прямом обращении по ID.

## Ошибки для интерфейса

Формат существующий — `{"error":{"code":"…","message":"…",…}}`.

| Код HTTP | `error.code` | Что показать |
|---|---|---|
| `401` | `AUTH_REQUIRED` | Предложить повторный вход. |
| `404` | `WORKSPACE_NOT_FOUND`, `PROJECT_NOT_FOUND`, `WORKFLOW_NOT_FOUND`, `RUN_NOT_FOUND` | Показать, что ресурс недоступен. Если перестало быть доступно выбранное пространство, обновить список и перейти в личное. |
| `403` | `WORKSPACE_OWNER_REQUIRED` | Показать, что действие доступно владельцу пространства. |
| `409` | `TEAM_WORKSPACE_REQUIRED`, `PROJECT_NOT_PERSONAL` | Перенос поддерживается из личного пространства в командное. |
| `409` | `WORKSPACE_REPOSITORY_EXISTS` | В команде уже есть такой репозиторий. Исходный проект остаётся в личном пространстве. |
| `409` | `PROJECT_CHANGED_RETRY` | Обновить список и предложить повторить добавление проекта. |
| `422` | `INVALID_REQUEST`, `REPOSITORY_NOT_ALLOWED` | Показать ошибку поля или ограничение учебного репозитория. |

## Что сделать на фронтенде

1. После подтверждения сессии загрузить пространства. Выбор хранить в клиенте по ID аккаунта или в URL. Проверить все страницы, прежде чем считать сохранённое пространство недоступным и выбирать личное. Серверный endpoint переключения не нужен.
2. Передавать выбранный ID в список и создание проектов, включая поиск или создание репозитория при сохранении из редактора. Сценарии и историю загружать только для проектов из ответа выбранного пространства. В ключи кэша включать ID пространства.
3. При переключении отменять предыдущие запросы и подписки SSE, сбрасывать список, проект и историю старого пространства. При наличии несохранённых изменений в редакторе дать пользователю выбрать, как поступить с черновиком.
4. В личном проекте показать «Перенести в команду». Среди вариантов оставлять командные пространства с ролью `owner`. Перед запросом показать, что команда получит доступ к проекту и связанной истории. Реквизиты проекта, CI-токены и настроенные получатели остаются привязаны к проекту. Проверка Telegram-адресатов по-прежнему использует профиль, под которым проект был создан. На `200` обновить списки исходного и целевого пространств. Текущие ссылки на проект, сценарий и запуск остаются действительными для участников.
5. Приёмка в браузере — создать команду, перенести личный проект с существующим запуском и переключиться между личным и командным пространствами. Проверить исчезновение проекта из личного списка и сохранение сценария и истории по прежним ID. Второй аккаунт вне команды получает `404` по прямой ссылке.

Приглашения и управление составом команды относятся к [#4](https://github.com/ReiBestFun/Cybergarden2026_cin/issues/4). Старые проекты без владельца назначает оператор существующей командой `claim_projects` после подтверждения получателя. Они попадают в его личное пространство и оттуда могут быть явно перенесены.
