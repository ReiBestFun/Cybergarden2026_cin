# Локальная приёмка CyberFlow

Два локальных пользователя прошли вход через обработчики OAuth и получили отдельные серверные сессии. Тестовый адаптер подставил две идентичности GitHub при обмене кода. Остальные шаги использовали приложение, отдельную PostgreSQL с миграциями, GitHub для получения исходников, Ollama и локальный SMTP-приёмник.

| Что проверили | Результат |

| Журналы | Первый владелец сменил срок аудита на 45 дней. Второй увидел эту политику в общей команде и получил HTTP 404 для политики, записей и выгрузки другого пространства. |

## Сценарий защиты на пять минут

1. **Кому помогает сервис.** Разработчик Kotlin/Spring получает находки по коду, зависимостям и секретам на одном коммите. Покажите в редакторе три параллельные проверки и узел объединения.
2. **Два пользователя.** Первый публикует командный шаблон и создаёт приглашение с ролью владельца. Второй входит в другом профиле браузера, принимает приглашение и копирует шаблон в проект команды. В копии выбирает почтового получателя и нажимает «Запустить». Привязки получателей задаются при копировании.
3. **Результаты и объяснения.** Откройте статусы восьми узлов, одну подтверждённую находку и предупреждение SCA о покрытии. Сопоставьте путь и исправление в JSON и Markdown. В разделе AI покажите рекомендацию и привязанную к исходной находке ссылку. В почтовом приёмнике откройте тему и вложение с тем же результатом.
4. **Три дополнительных сканера.** На отдельных синтетических входах `application.properties` с `server.error.include-stacktrace=always` даёт `sast.error-stacktrace` на строке 1. В `Demo.kt` учебный вызов `DigestUtils.md5Hex(password)` даёт `sast.weak-password-hash` на строке 1, а `logger.info(token)` — `sast.sensitive-logging` на строке 2. Входы и ожидаемые правила находятся в [сквозной проверке](acceptance.py).
5. **Архитектура и права.** Покажите путь API → очередь PostgreSQL → воркер сканирования → воркер SMTP. В «Настройки команды → Журналы» дайте участникам просмотр, затем покажите отказ в экспорте с ролью участника. Откройте запись об изменении политики.
6. **Проверка PR.** Покажите состояния PR gate в таблице ниже. Для включения обязательной проверки на целевом репозитории нужен его администратор.

## GitHub PR gate

Выполненный локально экспортированный шаг GitHub Actions проверяет SHA последнего коммита PR. Тест запускает PowerShell из YAML и перехватывает команду публикации статуса.

| Вход шага | Ожидаемый и полученный GitHub status |
| --- | --- |
| Анализ завершён, порог пройден | `success` |
| Превышен порог критичности | `failure` |
| Ошибка обработки, устаревший SHA или неполный анализ с решением `passed` | `error` для каждого случая |

При проверке на GitHub у `TBagirov/training` было 0 PR, список workflows пуст, у учебного коммита 0 опубликованных commit statuses. Текущий аккаунт имеет `pull=true`, `push=false`, `admin=false`. Живой статус на PR и обязательность проверки остаются неподтверждёнными. В предыдущей локальной проверке на том же учебном SHA gate вернул `blocked` из-за критической находки. [Целевой репозиторий](https://github.com/TBagirov/training/pulls) · [Протокол задачи #13](https://github.com/ReiBestFun/Cybergarden2026_cin/issues/13#issuecomment-7069696244)

## Как повторить

Из корня проекта установите зависимости `backend/requirements-dev.txt`, запустите локальную Ollama с моделью `mistral:latest` и укажите в `TEST_DATABASE_URL` отдельную пустую PostgreSQL. Для каждого повтора создавайте свежую тестовую БД. Для другой установленной модели задайте `DEMO_MODEL`. Потребуется доступ к публичному учебному репозиторию. Письмо принимает временный SMTP-сервер на loopback.

```bash
DEMO_OUTPUT=./demo-output python -m pytest -q docs/demo/acceptance.py
python -m pytest -q backend/tests/test_workspace_logs.py backend/tests/test_github_pr.py
```

Первый запуск сохраняет `findings.json`, `report.md` и `result.json` в выбранный каталог. Второй проверяет роли, отсутствие секретов, архивирование, сроки по типам журналов и PR gate. Для исполнения шагов из YAML требуется `pwsh`.
